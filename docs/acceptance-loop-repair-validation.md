## 已实现行为

1. `assessAcceptance` 一次汇总全部可确定的阻塞项。完成工具返回兼容的 `ok/error` 与结构化 `acceptance`；模型上下文使用同一诊断。反馈区分网页运行、浏览器交互、静态检查及具体验收条件，包含目标、原因、原报告、变动文件或失败检查和补验提示。
2. 新报告保存版本为 1 的检查证据。静态检查按文件拆分，同一验收条件的断言整体判断；执行报告另存实际依赖、入口及精度。对同一目标和版本使用最新完整结果，不能以另一入口的成功代替，也不能从失败断言组挑出通过项。
3. 保留 `RunnerAction.Inputs` 全量执行快照及原作业、运行 epoch、指令版本、输出旧 hash 校验。验收依赖的缩小不影响结果提交保护；作业登记时另保存验收计划，恢复旧作业时不套用后来修改的条件。
4. 新证据核对正式条件、排序去重后的路径与必用输入约定，计划编号仅用于追溯。修改计划说明、重新保存计划可以复用仍有效的新证据；新增要求或必用输入不能借旧证据直接通过。
5. 完成申请排除总结文字，按每项未解决阻塞的真实条件持久计数。默认第 3 次相同失败后拦截原样重试，恢复预算沿用 2 次；普通继续、改派及序列化后计数保留。补齐一项不清空其他问题的历史，真实补齐后允许完成。其他工具保留原指纹算法；旧失败记录不作猜测性迁移。
6. 预览入口和界面可预览状态也使用同一文件依赖比较，避免修改无关产物后验收仍有效但预览消失。预览只证明已有构建与文件匹配，不授予任务验收通过。

## 已知限制与后续验收

- Python、JavaScript/TypeScript 脚本和 Go 可能读取任意输入，继续使用全量快照。只有可信网页构建及静态检查能够缩小依赖。
- 网页依赖包含构建器列出的文件、HTML/CSS 资源；为覆盖扩展名解析和配置变化，首版保守记录完整路径集合以及构建时全部 JSON 配置候选。因此新增或删除无关文件、修改未实际使用的 JSON 候选仍可能要求补验；修改既有未引用 PPTX 或文档正文不会影响网页检查。
- 旧报告继续保留旧任务、指令和计划边界；旧执行器全快照额外核对路径集合，避免新增模块被忽略。旧计划编号变化、目标信息不完整等情况仍需有针对性地补验，不伪造或迁移历史成功。
- 自动断言执行和证据管理不能代替未覆盖的用户语义与人工验收。本次没有重跑原线上模型任务，也没有验证当前 PPTX 的 PowerPoint 原生打开。生产发布记录见下文。
