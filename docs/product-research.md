## 1. 调研方法与证据范围

已阅读用户提供的需求文档和社区咖啡馆共享对话，并通过浏览器查看 Atoms 首页、构建模式菜单、Team Mode 开关、问题卡、计划卡、执行步骤、版本列表及桌面/移动预览。已阅读官方入门、聊天、协作、预览、历史、源码、发布及故障排查说明。

证据按以下口径使用：

- **页面观察**：本轮实际打开并查看的功能或状态。
- **用户说明**：用户明确补充的使用方式与截图。

## 2. 产品形态

Atoms 是通过自然语言驱动智能体工作的产品。用户从描述目标开始，在同一个项目里查看工作过程、检查产物、提出修改并保留版本。首页承载创建入口和项目导航，项目工作台承载对话、产物与查看器。[官方入门](https://help.atoms.dev/en/articles/12129543-welcome-to-atoms)

**用户纠正（2026-11-11）：产物不限定网页，咖啡馆只是一个网页开发案例。** 追加查阅的官方 Output types 文档明确包含浏览器项目、移动应用、视频及文档、报告、演示文稿等文件结果；产物类型与 Build/Plan 等工作模式是不同维度。上一版以网页概括所有产物，范围过窄，现已修正。这里描述的是原产品能力，并不表示本 Demo 首版承诺支持所有格式。[产物类型](https://help.atoms.dev/en/articles/12129547-output-types)

核心价值是持续完成“需求到可使用结果”的循环。网页类产物的按钮、菜单和表单应当真的工作，生成文件和版本应当与展示结果对应；文档与数据任务则应交付对应内容和文件，而非强制包装成网页。[快速开始](https://help.atoms.dev/en/articles/12129545-quick-start)

## 3. Build、Plan 与 Team Mode

用户特别说明：共享咖啡馆对话采用 **Plan** 模式。用户截图和本轮当前页面都显示以下两个选项：

| 选择 | 当前页面含义 | 可得出的结论 |
| --- | --- | --- |
| Build | General building mode | 通常构建入口；不能把 Plan 对话中的审批流程套到所有 Build 请求上 |
| Plan | Mike plans and assigns the build | 由 Mike 规划并分派构建；咖啡馆案例展示了澄清、计划确认、交接和执行 |
| Team Mode | 输入区加号菜单中的独立开关 | 与 Build/Plan 不同维度；本轮观察到 Build 被选中时该开关开启 |

官方 Input Chat 文档目前仍将第二项写为 **Goal**，但描述与当前 Plan 选项相同。本 Demo 采用当前页面名称 **Plan**，不把 Goal 设计成第三种模式，也不根据名称差异推断隐藏的路由规则。[输入区文档](https://help.atoms.dev/en/articles/12129552-input-chat)

官方协作文档介绍：Team Mode 关闭时由 Alex 处理，开启时可由 Mike 和专家协作，并支持提及角色。角色可用性还与项目类型有关。因此 **Build 不等于单智能体，Plan 也不能与 Team Mode 简单画等号**。[智能体协作](https://help.atoms.dev/en/articles/12129548-working-with-agents)

本轮没有在 Atoms 发起新的付费构建，尚未通过新的 Build 请求逐项验证其所有分支。Demo 中“Build 默认不强制计划审批、Plan 审批后执行”是基于可见模式说明和案例提出的明确产品约定，详见需求规格。

## 4. 共享案例中看到的主流程

参考：[社区咖啡馆项目对话](https://atoms.dev/share/9a55f6c2e3134bb085108fe5d1ae1804/v3)。

1. 用户提出咖啡馆网站需求。
2. Mike 用问题卡收敛功能范围；问题分步展示，包含范围与视觉主题选择。
3. 计划卡总结目标，用户确认后进入实施。
4. Mike 向 Alex 交接明确范围与约束；执行卡可展开，展示读取文件、写入文件、运行检查等活动。
5. 工程师报告结果，协调者追问证据不足之处，再进行有边界的修正。
6. 过程中出现额度限制提示；用户随后要求继续，对话延续原任务。
7. 交付形成命名版本。页面列出了首次页面、移动可读性调整、菜单价格集中维护三个版本。
8. 用户继续问如何维护商品和价格，团队围绕已有项目修改并产生下一版本。

案例说明：澄清与确认会影响执行范围；检查结果会改变下一步动作；后续需求依赖当前项目上下文。它不证明每个项目都会调用所有角色，也不证明文字报告中的所有测试都已由本轮独立验证。

## 5. 界面与能力拆解

| 区域 | 本轮证据 | 对 Demo 的启示 |
| --- | --- | --- |
| 首页 | 自然语言输入、Build/Plan 菜单、项目入口；Team Mode 位于另一菜单 | 模式应在发送前可见，项目应能再次打开 |
| 项目对话 | 用户消息、角色身份、问题卡、计划卡、步骤卡、版本卡 | 对话需要承载动作与产物，而不仅是文本 |
| 工作区域 | 左侧对话、右侧应用预览，顶部工具栏 | 保持需求与结果并排可见；窄屏使用切换面板 |
| 执行过程 | 展开的步骤中可见读写文件、命令、视觉检查等活动 | 展示真实步骤摘要及结果，不模拟进度或检查成功 |
| 预览 | 已实际切换桌面和移动模式，并看到对应布局变化 | 预览必须加载本版本产物，允许用户试用交互 |
| 源码 | 官方描述文件树、查看/编辑、差异与导出 | 首版可先做查看与下载，手工编辑另行评估 |
| 历史 | 案例出现 v1–v3；官方描述历史预览、恢复和 Remix | 用版本承载迭代；查看历史与恢复当前状态应有明确区分 |
| 发布 | 官方区分项目分享与成品发布，修改后需另行更新线上版 | 工作台在线访问、预览链接、成品分享链接是不同概念 |

## 6. 首版范围建议

优先做好两种入口共用的一套生成与迭代能力：

- Build：输入清楚的需求后直接构建；信息确实不足时才补问。
- Plan：问题澄清、可修改计划、明确确认，然后构建。
- 两条路径均按需求生成对应产物并保留版本；网页提供交互预览，文档、数据和代码提供相应查看与下载；持续对话能在已有产物上修改。
- 平台保存项目、任务、消息、计划、运行状态、已保存中间产物、步骤检查点及成功版本；刷新与服务重启后仍可读取。
- 用户选择继续时，应复用已保存工作状态处理剩余步骤。新的运行记录不等于清空文件；模型尚未返回的生成过程与未完成工具内部状态不在恢复保证内。这是本 Demo 的产品要求，尚未实现，也不是对 Atoms 内部机制的实证描述。
- 智能体首版建议覆盖 Mike、Emma、Bob、Alex、David，按任务需要调用；详细职责与产物示例见需求规格。Iris、Sarah、Adrian 暂缓。
- 将版本差异与恢复作为首个扩展能力，帮助用户判断改动并回到可用状态。

首版不建议全面覆盖营销、广告、支付、视频、模型竞赛、外部服务连接及任意后端应用生成。以上为范围建议，待用户确认。

## 9. 本 Demo 的中断与智能体范围补充

“保留最后成功版本”与“保存未完成任务的中间工作”是两项不同要求。上一版没有完整写明后者，因此需求 v0.2 增加了逐文件保存、步骤检查点、继续/重做区分以及中断后的恢复验收。恢复承诺以平台确认保存的工作为界，不能承诺找回模型尚未返回或工具尚未完成写入的内容。

官方常规角色包含 Mike（协调）、Emma（产品）、Bob（架构）、Alex（工程）、David（数据），另有 Iris（研究）、Sarah（搜索优化）、Adrian（广告）。本 Demo 建议先落地前五者的必要能力，按需求交接；角色数量不代表每次必须执行五轮，也不代表每个角色必须使用不同模型。[智能体协作](https://help.atoms.dev/en/articles/12129548-working-with-agents)
