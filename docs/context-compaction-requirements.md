# Atoms 自动上下文压缩需求

日期：2026-11-12。需求和 [技术方案](context-compaction-design.md) 已确认。

## 目标

复杂任务的旧消息和工具结果累积时，Atoms 自动缩短发给模型的上下文，让任务继续使用现有产物和检查点。用户无需缩小原需求或从头重做。

线上已有复现。一个任务积累了 156 个检查点后，最近两次点击「继续任务」都在发出第一次模型调用前因请求超过 128 KiB 而失败。提高每分钟或单轮调用额度无法解决单次请求过大的问题。

## 范围

- 覆盖线上 JSON 工具模式下的所有角色。首次执行和从检查点继续使用同一套规则。
- Atoms 单次模型请求体上限默认为 500 KiB，可通过服务端配置调整。发送前按序列化后的字节数检查大小，压缩触发点和压缩目标按当前上限的百分比计算。短任务沿用现有历史裁剪规则。
- 压缩后的输入保留当前目标、用户已确认的要求及最新更正、已批准计划、验收条件、当前产物和检查状态、未完成事项，以及继续下一步所需的近期消息和工具结果。必要时模型仍可按路径读取当前文件。
- 压缩只改变发给模型的内容。原始消息、工具记录、检查点、文件和版本可继续访问。已通过的审批和检查以应用记录为准，摘要不得代替批准或生成验收结论。
- 一旦连必要信息也无法放进单次请求，说明具体原因并保留进度。超限请求不发送，不消耗一次模型调用。已发送的请求仍遵守现有的单轮、每日和 TPM 额度。

## 验收标准

| 场景 | 可验证结果 |
| --- | --- |
| 按当前上限触发压缩 | 构造请求刚好低于、等于和高于触发比例的长历史。等于或高于时启动压缩，发送的实际请求不超过当前配置上限。降低配置后触发点随之下降。 |
| 继续此前因长历史超限的任务 | 请求在配置上限内成功发出，模型从已保存的检查点推进至少一个后续步骤，文件和检查点可核对。若调整上限后这条历史未达到触发点，另用长历史样本验证压缩确实生效。 |
| 同一个任务多次压缩 | 连续多次压缩后，模型仍能使用已确认的需求和最新更正，区分已完成与未完成动作。已提交的写入不会因压缩被再次执行。 |
| 审批和验收 | 未批准的任务仍等待批准。旧文件版本的通过报告不得替代当前文件的检查。 |
| 不可压缩的必要输入过大 | 提示造成超限的原因，保留已有产物，未发送超限请求。 |
| 普通短任务 | 不触发新压缩，问答、工具调用、JSON 格式重试和网关 TPM 重试照常工作。 |

验证先用可控模型返回复现边界，再用保留的长任务验证真实续跑。记录压缩前后的实际请求字节数和完成的步骤，区分续跑成功与最终交付完成。
