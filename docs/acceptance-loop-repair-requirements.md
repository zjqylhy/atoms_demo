# 产物验收循环修复需求

日期：2026-11-13。状态：需求与技术方案均已确认；编码与验证已完成，等待人工验收。

## 问题与目标

线上 PowerPoint 转换任务的两个运行共调用模型 99 次，17 次完成申请均被拒绝。只读快照回放已逐次复现拒绝原因。相关证据保存在 `artifacts/acceptance-loop-20261113/`。

本次目标：让 Agent 能准确识别尚未满足的交付条件，复用仍有效的检查结果，并在相同失败条件下停止无效重复。

当前每个文件已有独立的内容 hash，同时项目清单也有整体摘要。问题不是缺少单文件 hash，而是运行报告记录了整个项目的文件依赖；修改计划也会使旧报告整体失效。防重复机制包含完整工具参数，交付总结变化会被当作条件变化。

## 需求范围

### R1：交付失败反馈明确、完整

- 一次反馈列出可以确定的全部阻塞项，包括对应文件或验收条件，以及缺少、检查失败、证据过期等具体原因。
- 明确区分网页运行与浏览器交互检查。已有浏览器检查通过、缺少网页运行时，必须明确指出需要补充哪类检查。
- 对失效报告说明依据，例如实际依赖文件内容变化、验收要求变化；不能只返回笼统的“当前版本未通过”。
- 反馈使用实际文件、报告和检查结果，不能将模型自述作为通过证据。

### R2：按实际依赖判断检查是否仍有效

- 沿用单文件内容 hash；一个文件变化应影响该文件及依赖它的检查，不影响无关检查。
- 例如：修改 `app.js` 后，使用该脚本的网页验收失效；仅修改与网页无关的 `slides.pptx` 时，该网页验收仍有效。
- 检查涉及多个输入或生成输出时，必须覆盖相关依赖，不能退化为只核对入口文件。
- 无法可靠确定依赖时采取保守判断，并说明需要重新验证的原因。
- 计划的实际验收要求和对应路径未变时，不能仅因计划编号或说明文字变化让相关证据失效；实际要求发生变化时，原报告不能自动证明新增或修改后的要求。
- 保留运行有效性、用户指令版本和迟到结果校验，避免旧运行覆盖新状态。

### R3：重复失败判定使用实际执行条件

- 相同输入、相同相关验收状态、相同失败原因下，仅改变交付总结等说明文案，必须累计为同一类重复失败。
- 无关文件变化、报告标识变化、重复登记相同结果，不能被当作解决阻塞项的新证据。
- 相关输入或验收证据实际改善后，允许再次尝试；不能把有效修正误判为无效重复。
- 沿用有限重试与恢复预算，触发限制时保留已保存文件、报告和检查点，并返回具体受阻原因。

## 验收标准

1. 针对本次只读快照，反馈准确列出网页运行、当前有效浏览器证据、网页和 PRD 静态检查等缺项；区分历史通过与当前有效。
2. 用固定样例分别验证：修改无关 PPTX 不影响网页检查；修改网页使用的 JS/CSS 会使其失效；修改真实生成输入或输出使相关证据失效。
3. 计划仅改说明或重新保存时保留符合当前要求的证据；增加或改变验收要求时不能误用旧证据。
4. 只改变交付总结的重复失败能达到现有阈值；补齐真实缺项后可以继续完成。
5. 停止、续跑、新指令交接及迟到结果的既有保护继续有效。
6. 完成与改动匹配的回归测试和快照验证，保留明确的测试结果与未覆盖项；独立、已验证的代码改动按项目约定提交 commit。

## 交付边界

- 先完成需求确认，再产出技术方案；技术方案确认后编码与测试。
- 修复应适用于不同文件与任务，不按本次项目 ID、文件名或 PPTX 案例编写特例。
- 保留现有项目、产物和原始报告，不补写虚假的通过记录。
- 本次已完成的排查没有触发模型调用或修改生产任务；后续验证不能把未执行的线上验收记为通过。
